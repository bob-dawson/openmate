# 移动端同步设计 V2：消息增量 + revert 删除

> 状态：**已实现**（opencode v2.0.15 实测通过；Docker 容器端到端验证）
> 日期：2026-09-23
> 适用：opencode v2（本机实测 v2.0.15）
> 关联：`docs/design/会话同步设计.md`（V1 方案，已被本文替代）

## 1. 背景

opencode v2 的事件溯源架构下：

- V1 的 `message` / `part` 表已移除，唯一消息源是 `session_message`（+ `session_v2`）。
- durable 事件默认**不落库**（`Bus.configured({ persist })` 默认 false；官方 CLI `server-process.ts` 不传 `events.persist`，也无环境变量可开）。
  - 实测本机：`event` 表 0 行；`GET /api/experimental/session/:id/log?after=0` 只返回 `log.synced`，无任何事件。
- 官方全局 SSE `/api/event` 被明确定义为 **volatile**（"events during disconnection are missed"，慢消费者断流）。
- changes feed（hints / sweep_required）已在 commit `ff499c3603` 移除。

因此官方不提供任何"持久的删除增量"。官方客户端（web/TUI）采用的补偿方式是：实时 SSE 应用变更 + 重连/打开会话时**重拉投影快照**（`packages/client/src/solid/data.ts`、`packages/app/src/session/session-resolution.ts`、`packages/tui/src/routes/session/rows.ts`）。

## 2. 目标与非目标

### 目标

1. 正常消息增量：新增 + 就地更新。
2. **revert（删除）增量**：准确识别并删除本地已被服务端删除的消息。
3. 满足 `AGENTS.md` 的 Sync Constraints：**不依赖 SSE 保证正确性**；SSE 仅提升实时性。
4. 保留 OpenMate 的差异化能力：本地持久化、离线可查看。
5. 不依赖 opencode 开启 `events.persist`，不依赖插件，不依赖官方全量 resync。

### 非目标

- 不做全量 resync 作为常规手段（保留为极端兜底）。
- 不引入 Bridge 侧消息镜像表（对比机制由客户端驱动，Bridge 无状态）。
- 暂不处理"消息中间删除/重排"（当前交互方式下不会出现，见 §3）。

## 3. 核心不变量（源码依据）

1. **运行时唯一删除路径是 revert**：core 中唯一对 `session_message` 的 delete 在 `packages/core/src/session/projector.ts:751`（`RevertEvent.Committed` → `DELETE ... WHERE seq >= boundary.seq`）。其余为 append / update。
2. **存活集合 = 前缀 + 后缀**：revert 删除"当前存活集合的后缀"，多次 revert 合并后，被删消息在创建顺序上仍是**一段连续区间**。即：找到公共前缀长度 `L` 与公共后缀长度 `R`，则本地 `client[L .. n-R-1]` 即全部被删消息。
3. **id 单调**：`SessionMessage.ID = "msg_" + ascending()`，按创建顺序字典序递增（官方客户端即用 `item.id >= event.data.to` 截断）。
4. **seq 单调不复用**：`event_sequence` 用 `max()` 保序；revert 会推进 seq，故 revert 后新消息 seq 更大。
5. **本地连续性**：Android 本地为「快照窗口 + 增量追加 + 向前翻页」，是服务端列表的连续子区间（除非未来支持隔段加载）。

> 说明：即使不变量 2/5 被破坏（例如未来出现中间删除），§5 的门闩/修复仍是精确的——门闩可能产生假阳性（多触发一次修复），修复按 id 集合判定存在性，结果始终正确。

## 4. 设计原则

- **正确性来自对比，不来自 SSE**：每次增量同步都做一次轻量删除检测；SSE 只用于提前触发。
- **两阶段：O(1) 门闩 + 仅删除时定位**：revert 频率远低于正常同步，故删除检测折进增量同步，常态只付 O(1) 成本。
- **精确而非启发式**：门闩基于"区间内只可能删、不可能增"的结构性质，无盲区（见 §5.1）。
- **resync 退休为兜底**：仅当对比无法收敛（如本地数据损坏）时使用。

## 5. 两阶段删除检测

revert 频率远低于正常消息同步，故分两级：**常态 O(1) 门闩，仅在确有删除时才做定位**。

### 5.1 一级：区间计数门闩（O(1)，折进增量同步）

门闩**折进现有 `/messages` 增量请求**（不额外占用往返）：客户端在同步前取本地区间 `[firstId, lastId]` 与条数 `count` 作为 query 参数，响应多返回一个 `serverCount`。

```
GET /api/bridge/sync/session/{sessionID}/messages?since=<ts>&limit=<n>&firstId=<>&lastId=<>&count=<>
→ { "messages": [...], "hasMore": bool, "maxSeq": int, "serverCount": int | null }
```

```sql
SELECT count(*) FROM session_message
WHERE session_id = ?1 AND id >= ?2 AND id <= ?3;
```

**判定**：`serverCount == count` ⟺ 区间内无删除。

**为什么精确（非启发式）**：

1. 新消息的 id 恒大于客户端 `lastId`，因此区间 `[firstId, lastId]` 内**只可能发生删除，不可能发生新增**（门闩用"同步前"的区间，仍然正确）。
2. 客户端本地是连续子区间（不变量 5），故服务端在该区间内的存活集合是客户端集合的**子集**。
3. 因此恒有 `serverCount <= count`，且 `serverCount < count` **当且仅当**区间内有消息被删。
4. 无假阴性；唯一假阳性是客户端自身存在漏同步空洞，此时会多触发一次精确修复，属自愈。

> 常态成本：约 +50 B / 次、0 额外 RTT。

### 5.2 二级：精确修复（仅门闩不通过时执行）

按本地条数 `n = count` 自适应选择，`d = count - serverCount` 为删除条数：

**方案 A（n ≤ 100，1 RTT，最简）**：`GET .../ids?fromId=&toId=` 返回区间内服务端存活 id，客户端差集删除。
- 流量约 `33 × n` ≤ ~3.3 KB。

**方案 A′（n > 100，2 RTT，O(√n) 流量）**：
- 第 1 轮：客户端按 `K = ⌈√n⌉` 取采样 id（位置 0, K, 2K, …），
  `POST .../probe { baseId, ids: [...] }` → 服务端返回各采样点前缀存活计数 `counts[i] = |alive ∩ [baseId, ids[i]]|`；
  客户端以 `counts[i] == (i+1)` 判定是否越过删除起点，把 `L` 夹到一个 K 块内。
- 第 2 轮：对该块调用 `GET .../ids?fromId=&toId=`（≤ K 个 id）→ 精确差集。
- 流量约 `66√n` 字节；往返固定 2 次。

> 由不变量 2，被删为一段连续区间，故定位 `L` 后删除集即 `c[L .. L+d-1]`（`c` 为本地按序 id）。方式 A 的差集结果天然对任意删除形态成立。

### 5.3 排序约定

- 客户端与服务端统一按 **`(time_created ASC, id ASC)`** 对齐（Android 现有排序即 `timeCreated, id`）。
- `seq` 与 `(time_created, id)` 在实测中一致（id 由事件 id 派生、单调）。以 `(time_created, id)` 为规范排序；若将来出现不一致，退化为精确 id 集合对比（方式 A 天然正确）。

## 6. 触发机制（不改动 SSE）

门闩的正确性依赖"同步会被触发"，而不依赖 SSE 是否送达：

- **现有 SSE**：Bridge 已把 `session.revert.*` 作为轻量通知转发（`events/filter.rs` 白名单），Android 收到即触发 `incrementalSync`（`EventDispatcher`）→ 低延迟。
- **轮询兜底**：Android 每 15s 轮询（`POLL_INTERVAL_MS = 15_000`）触发 `incrementalSync`。即使 SSE 漏了 revert 通知，下一次轮询也会跑门闩并修复。
- 因此**本次不改动 Bridge 的 SSE 处理**：不做非惰性启动、不改重连间隔、不做内联 revert 捕获。`revert_log` / `/reverts` 已在实现中清理移除（见 §8 改动清单）。
- 已知取舍：他人 staged/cleared 的 revert 预览不会实时同步（仅影响 UI 提示；committed 删除仍由门闩保证）。

> 结论：SSE 只影响"多快看到"，门闩保证"最终一定对"，满足 Sync Constraints。

## 7. 数据库 / 数据模型

### 7.1 服务端（opencode，只读）

`session_message` 关键列：`id, session_id, type, seq, time_created, time_updated, data`，唯一索引 `(session_id, seq)`。

### 7.2 Bridge（bridge.db）

- **无新增表 / 状态**：门闩与修复都是对 opencode `session_message` 的只读查询。
- 已移除 `revert_log` 表及其查询（`get_reverts_since` / `cleanup_old_reverts`）与 `/reverts` 路由（不在正确性路径上）。

### 7.3 Android（Room）

- 游标仅需 `lastTimeUpdated`（消息增量）。
- **无 Room 版本变更**：不再使用 `lastRevertTimestamp`（保留列或后续清理），不新增 `lastRevertId`。
- 现有 `session_message` / `session_message_full_content` 表不变。
- 本地排序统一 `(timeCreated, id)`。

## 8. 客户端算法（Android）

### 8.1 增量同步流程（替换现 `doIncrementalSync`）

1. 同步前取本地区间 `firstId / lastId / count`。
2. 拉消息增量：`GET /messages?since=<lastTimeUpdated>&firstId=&lastId=&count=` → upsert（新增 + 更新）；响应含 `serverCount`。
3. **门闩**：`serverCount == count` → 无删除，结束（常态）。
4. **修复**（仅门闩不通过时）：
   - `n ≤ 100`：`GET /ids?fromId=&toId=` → 差集删除。
   - `n > 100`：`POST /probe`（采样 √n 夹逼）+ `GET /ids`（小区块）→ 差集删除。
   - 最早被删 id 即 revert 边界，用于更新会话标记。
5. 更新 `SyncStateEntity`（`lastTimeUpdated`）。

> 顺序：先消息（补齐新增/更新），再门闩/修复（删多余）。两者都基于服务端当前状态，顺序无严格依赖。

### 8.2 删除语义

- 删除完全由门闩/修复处理：本地区间内、服务端 id 切片外 → 删除；最早被删 id 即 revert 边界。
- 不再依赖 `/reverts`，也移除 id 内嵌时间戳解析（`extractStoredTs` / `MOD_2_36`）。

### 8.3 兜底 resync

保留现有 `rollbackSeq` / 重新 `initSync` 能力，仅在门闩/修复连续失败或本地数据损坏时手动触发。

## 11. 边界情况

| 场景 | 处理 |
|------|------|
| 本地为空（冷启动） | 走 `initSync` 快照，跳过门闩 |
| 服务端会话已删除 | `/messages` 返回空/404 → 删除本地该会话 |
| `firstId`/`lastId` 已被删 | 用 `id >= firstId AND id <= lastId` 仍能取到存活切片；差集正确 |
| 本地有空洞（非连续） | `serverCount < count` 假阳性 → 走修复，按集合差集自愈 |
| 同毫秒多条 | 统一 `(timeCreated, id)` 排序，id 兜底 |
| revert 后立即可追加新消息 | 新消息 id > lastId，不影响门闩；修复用差集仍精确 |
| Bridge 与 opencode 短暂断连漏事件 | 下次同步的门闩检测到 `serverCount < count` → 修复校正 |
| 极大历史（数千条） | 修复走 A′（2 RTT、O(√n) 流量） |

## 12. 测试计划

**Bridge（Rust 单测/集成）**
- 区间存活计数：无删除、有删除、边界 id 被删、空区间。
- 区间存活 id 切片：正常、firstId/lastId 被删。
- 采样前缀计数（`/probe`）的边界与越界。

**Android（Kotlin 单测，手写 fake，Truth）**
- 门闩通过时不改数据。
- 门闩不通过时删除正确 id 集合、更新边界标记。
- n ≤ 100 走 A、n > 100 走 A′。
- 离线期间 missed revert → 下次同步门闩检测并修复。

**端到端（simulator）**
- 正常多轮对话增量。
- 另一客户端执行 revert → 本端窗口正确删除。
- 断网期间 revert → 恢复后门闩检测并修复。
